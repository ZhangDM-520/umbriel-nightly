# Branch ownership — the maintained branch contracts

Standing contract for the pull requests this fork carries. The machine-readable copy of these rows and each branch's gate lives in the maintainer's warehouse, together with `branch-status.sh`, the probe that reads it; this file is the reviewable copy that travels with the integration branch. Update both in the same round.

Upstream squashes every pull request (`d3c85928 … (#585)`), so a branch here is a queue of commits, not a history: rebasing is lossless and a force-push costs nothing that upstream keeps.

## Conflict surface

The previous eleven-branch set measured by `git merge-tree --write-tree`: **42 clean of 55, thirteen collisions.** Re-run the probe (`git merge-tree --write-tree` over every pair) before repeating a count claim — a clean pair today says nothing about a pair introduced tomorrow. A conflict is therefore always one of three shapes:

1. **Upstream drift in a shared header.** #715 lost an include block to this shape; a rebase removes it, and it does not come back once the branch's merge commits are gone.
2. **Upstream moved or redesigned the code the branch edits.** #570 hit the redesign form: upstream replaced `raiseTransientTree()` with `raiseInOrder()` + `collectTransientTree()`, and no textual union compiles. #742 and `feat/resize-physics` hit the same form when upstream `2a6f837e` rewrote the scratchpad presentation and `View::setMaximized`; both were rebased. A rebase fixes both; neither is a `nightly` union.
3. **A sibling fork branch, never upstream.** Those belong to the `nightly` replay, where both sides exist, not to the PR branch.

The thirteen collisions, all sibling pairs: `feat/resize-physics` against `floating-minimize-animation` (`animation.md`, `view_state.cpp`), `fix/drag-deform-settle-crop` (`view_animation.cpp`/`view.cpp`/`view.h`/`view_lifecycle.cpp`), `fix/ram-footprint` (`effect_registry.cpp`), `fix/resize-lag` (`cursor.cpp`/`cursor.h`/`view.cpp`/`view_floating.cpp`/`view_state.cpp`), `feat/scratchpad-restore-fade` (`animation.md`) and `feat/scratchpad-drop-adopt` (`animation.md`, `scratchpad.cpp`); `floating-minimize-animation` against `feat/scratchpad-restore-fade` and, inheriting it because it is stacked, `feat/scratchpad-drop-adopt` (`animation.md`, `view.h`, `view_animation.cpp`); `background-blur-protocol` against `fix/overview-scratchpad-fade` (`overview.cpp`); `scratchpad-close-animation` against `fix/overview-scratchpad-fade` (`scratchpad.h`); `fix/resize-lag` against `feat/scratchpad-drop-adopt` (`cursor.cpp`, `cursor.h`); and `fix/overview-scratchpad-fade` against `feat/scratchpad-restore-fade` and `feat/scratchpad-drop-adopt` (`scratchpad.md`).

`feat/resize-physics` is the last of the resize family to be cut and shares a file with almost all of them, which is why `nightly` carries it as C6. Row 19 carries C11 for the same reason on the scratchpad side.

## Rules

- A fix goes on the branch that owns the surface, never on another branch and never on `nightly`.
- Rebase to sync with `upstream/main`; never merge. Merge commits are what turned #715 and #570 into conflicts.
- Force-push only with `--force-with-lease`, and only after showing the owner the diff and the gate results.
- `nightly` is rebuilt on `upstream/main`, never appended across a base move. Appending rows to an unmoved base is allowed at the owner's decision and is recorded in the manifest, which is the record of integration order.
- Conflict ownership is decided by `upstream/main`, not by `nightly`. `git merge-tree --write-tree upstream/main <branch>`: clean means the branch is fresh, and the collision it makes inside `nightly` is `nightly`'s to union; colliding means it is stale, and the fix belongs to its owner.
- Never `git add -A` in `~/Projects/umbriel-dev`; stage explicit paths.
- This file lives on `nightly` only and is never proposed upstream. A rebuild starts from `upstream/main`, so the bookkeeping commit that writes this file and `docs/nightly-manifest.md` must run after every replay.
